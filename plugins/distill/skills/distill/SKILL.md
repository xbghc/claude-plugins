# Distill — 会话经验提炼器

## Overview

回顾会话中的试错过程，把"踩过的坑"编码成下次能避开的知识。

**Core principle:** 摩擦点 = 信号。确认 = 闸门。路由 = 手艺。

## The Iron Law

```
NO WRITES WITHOUT EXPLICIT USER CONFIRMATION
EXTRACT FROM FRICTION, NOT FROM A STRAIGHT-LINE SUCCESS
```

未经用户审批，不动任何文件。会话一帆风顺没摩擦时，如实说"无可提炼"，不要为了凑数虚构教训。

## The Workflow

```
WHEN distilling a session:

1. SCAN: 遍历完整对话历史，标记摩擦点
2. CLASSIFY: 摩擦（报错→修复、方案切换、反复试）vs 正向模式（一次成功的非显然技巧）
3. ROUTE: 每条经验 → skill（跨会话）/ CLAUDE.md（项目事实）/ 其他文档
4. PROPOSE: 结构化报告 + 完整新文件内容 + 修改项 unified diff
5. CONFIRM: 等待用户明确批准（全批 / 部分批 / 拒绝）
6. WRITE: 仅在批准后写入；只写被批准的项
```

## 摩擦信号 — 扫描清单

```
- 报错→修复循环：命令/代码失败后被修正
- 方案切换：方案 A 尝试后被放弃，改用方案 B
- 反复尝试：同一操作以不同变体多次执行
- 非预期行为：表现与预期不符，需排查
- 知识空白：信息在任务中途才被查到
- 配置发现：不显而易见的设置/参数/环境变量
```

每个摩擦点提取四要素：

```
- TRIED: 最初的（错误/次优）做法
- FAILED BECAUSE: 报错信息 / 非预期结果 / 放弃原因
- SOLUTION: 实际有效的做法
- ROOT CAUSE: 为什么第一次尝试会失败（缺上下文？错假设？版本问题？）
```

## 正向模式 — 次要扫描

一次成功但值得留档的非显然技巧：

```
- 涉及项目特有约定，难以凭直觉猜到
- 使用了不常见的 API 用法 / 参数 / 配置
- 代表一种可复用的工作流模式
```

从简。重心在摩擦点。

## Routing Decision

```
IF 经验在另一次会话、另一个任务中也有用:
  → skill（首选）
    IF 跨项目可复用: ~/.claude/skills/ 新建
    IF 仅本项目可复用: .claude/skills/ 新建
    IF 已有 skill 不完整: 更新已有 skill，不新建
IF 仅是本项目一次性事实:
  → CLAUDE.md（追加到相关小节，或新建 `## 经验教训`）
IF 是文档缺失导致的困惑:
  → README 或相关文档
```

**Priority:** Skill（新建或更新） > CLAUDE.md > 其他文档

**判断标准（一句话）:** "这条经验在*另一次*会话/任务中是否有用？" 是 → skill；否 → CLAUDE.md。

## Output Template

```
## Distill 报告

### 发现摩擦点：N 个

#### 1. [简短标题]
- **TRIED**: [最初的做法]
- **FAILED BECAUSE**: [根因]
- **SOLUTION**: [最终有效的做法]
- **ACTION**: 新建 skill `skill-name` / 更新 CLAUDE.md / 更新 `path/to/doc`

#### 2. ...

### 正向模式：N 个

#### 1. [简短标题]
- **DID**: [具体操作]
- **WORTH RECORDING BECAUSE**: [为什么值得记录]
- **ACTION**: ...

### 拟议变更

[每项行动展示：新文件给完整内容；修改项给 unified diff]
```

## Forbidden Behaviors

**NEVER:**
- 在用户批准前写任何文件
- 凭印象虚构摩擦（"顺便加一条 X 的注意事项"）
- 把未列入提议的修改混进 commit
- 重复记录已有 skill / CLAUDE.md 已覆盖的内容
- 跳过提议步骤（"直接建好算了"）

**INSTEAD:**
- 拟议报告里展示完整新文件内容
- 修改项给 unified diff
- 即使"显然该做"也等用户说 ok

## Skill Writing Rules（提议新建 skill 时遵守）

```
NAMING: 小写加连字符，描述性强，≤64 字符
DESCRIPTION: 包含具体触发条件 — 报错信息 / 工具名 / 症状表现
             写得"主动"，确保相关场景真的能激活
BODY:
  ## 场景 — 什么情况下需要这个知识
  ## 正确做法 — 分步骤、可直接照做
  ## 原理 — 为什么这样做是对的
TONE: 祈使句，给正确路径；不要罗列禁忌清单
```

## CLAUDE.md Update Rules

```
- 追加到最相关的已有小节；找不到则新建 `## 经验教训`
- 用祈使句："先执行 X 再执行 Y"
  ❌ 不要："我们发现应该先执行 X 再执行 Y"
- 简要说明原因："先执行 X 再执行 Y — 否则 Z 会静默失败"
```

## Rationalization Prevention

| Excuse | Reality |
|---|---|
| "这个太显然了，不用记" | 现在显然 ≠ 下次会话也显然 |
| "用户应该已经知道了" | 知道就不会出现摩擦了 |
| "试错是网络/服务偶发，没必要记" | 偶发的确跳过；可编码的不能跳 |
| "可能已经记过了，懒得查" | 必须查；有就提议*更新*，不重复新建 |
| "直接写文件更快" | 用户必须审批，跳过 = 越权 |
| "正向模式凑一条，报告好看" | 凑数稀释信号；摩擦不够就少写 |

## Common Mistakes

| Mistake | Fix |
|---|---|
| 把偶发故障当教训记录 | 不可复现就跳过 |
| 与已有 skill / CLAUDE.md 重复 | 先搜索；有就提议更新 |
| 没提议直接写 | 一律先报告 + 等批准 |
| 写成"以后注意点儿" | 编码具体规则 + 原因 |
| 把项目事实和跨项目 skill 混在一起 | 按"复用范围"路由 |
| 提议里只列动作不展示内容 | 新文件给完整正文，修改给 diff |

## Edge Cases

- **没有摩擦**：如实说"会话一帆风顺，无可提炼"。可选择记录正向模式，但不要强行扩写。
- **摩擦源自偶发因素**（网络抖动、服务暂时不可用）：跳过，没有可编码的知识。
- **经验已存在**：在提议前检查相关 skill + CLAUDE.md。重叠就提议*更新*，不新建。
- **用户只批准部分**：只写被批准的项；未批准的明确说"已跳过"。
- **跨项目 vs 仅本项目难判断**：默认放本项目（`.claude/skills/`），后续真用上再升级到全局。

## The Bottom Line

**摩擦是信号。确认是闸门。路由是手艺。**

不静默写盘。不虚构教训。不重复编码。
